# Requirements Document

## Introduction

The PDF Visualization Frontend provides a modern, responsive web interface for viewing and managing PDF documents generated by the Speckit Auto-AI backend. Users can browse all generated PDFs with rich metadata, including creation time, source files, titles, and categories, presented through an intuitive dashboard built with React and shadcn/ui components.

## Glossary

- **Frontend**: The React-based web application that users interact with
- **Dashboard**: The main view displaying all PDFs with their metadata
- **Backend_API**: The FastAPI service providing REST endpoints for projects, artifacts, and PDFs
- **Artifact**: A generated PDF document with associated metadata stored in the database
- **Project**: A collection of artifacts belonging to a repository or workspace
- **PDF_Viewer**: A component that displays PDF content within the browser
- **Metadata_Card**: A visual component showing artifact information (title, type, dates, source)
- **Category**: The artifact_type field classifying documents (spec, plan, task, constitution, other)
- **Source_Path**: The original markdown file path that generated the artifact

## Requirements

### Requirement 1: Project Dashboard

**User Story:** As a user, I want to see all my projects in a visual dashboard, so that I can navigate to specific project artifacts.

#### Acceptance Criteria

1. WHEN the Frontend loads, THE Frontend SHALL fetch projects from the Backend_API endpoint `/api/projects`
2. THE Frontend SHALL display each project as a clickable card with project name
3. WHEN a user clicks a project card, THE Frontend SHALL navigate to the project's artifact list view
4. IF the Backend_API returns an error, THEN THE Frontend SHALL display an error message to the user
5. WHILE the Frontend is fetching projects, THE Frontend SHALL display a loading indicator

### Requirement 2: Artifact List View

**User Story:** As a user, I want to see all artifacts within a project, so that I can browse generated PDFs.

#### Acceptance Criteria

1. WHEN a user selects a project, THE Frontend SHALL fetch artifacts from the Backend_API endpoint `/api/projects/{project_id}/artifacts`
2. THE Frontend SHALL display each artifact as a Metadata_Card showing title, Category, Source_Path, and creation timestamp
3. THE Frontend SHALL sort artifacts by creation time in descending order (newest first)
4. THE Frontend SHALL group artifacts by Category with visual distinction between categories
5. WHEN a user clicks a Metadata_Card, THE Frontend SHALL open the PDF_Viewer for that artifact

### Requirement 3: PDF Viewing

**User Story:** As a user, I want to view PDF documents in the browser, so that I can read the generated content without downloading.

#### Acceptance Criteria

1. WHEN a user selects an artifact, THE Frontend SHALL fetch the latest PDF version from Backend_API endpoint `/api/doc-versions/{version_id}/pdf`
2. THE PDF_Viewer SHALL render the PDF content within the browser using an embedded viewer
3. THE Frontend SHALL display the PDF title and metadata alongside the PDF_Viewer
4. WHEN the PDF fails to load, THEN THE Frontend SHALL display an error message with retry option
5. THE Frontend SHALL provide a download button to save the PDF locally

### Requirement 4: Metadata Display

**User Story:** As a user, I want to see clear, easy-to-understand metadata for each PDF, so that I can identify documents quickly.

#### Acceptance Criteria

1. THE Metadata_Card SHALL display the artifact title with prominent typography
2. THE Metadata_Card SHALL display the Category with color-coded badges (spec: blue, plan: green, task: orange, constitution: purple, other: gray)
3. THE Metadata_Card SHALL display the creation timestamp in human-readable format (e.g., "2 hours ago", "March 15, 2024")
4. THE Metadata_Card SHALL display the Source_Path with truncation for long paths and tooltip showing full path
5. THE Metadata_Card SHALL use shadcn/ui Card component for consistent visual styling

### Requirement 5: Responsive Design

**User Story:** As a user, I want the interface to work on different screen sizes, so that I can use it on desktop, tablet, or mobile.

#### Acceptance Criteria

1. THE Frontend SHALL use responsive grid layouts that adapt to viewport width
2. WHEN the viewport width is less than 768px, THE Frontend SHALL display artifacts in a single column
3. WHEN the viewport width is between 768px and 1024px, THE Frontend SHALL display artifacts in two columns
4. WHEN the viewport width is greater than 1024px, THE Frontend SHALL display artifacts in three columns
5. THE Frontend SHALL ensure touch-friendly interaction targets on mobile devices (minimum 44x44px)

### Requirement 6: Navigation

**User Story:** As a user, I want to navigate between projects and artifacts easily, so that I can explore the full document hierarchy.

#### Acceptance Criteria

1. THE Frontend SHALL implement client-side routing using React Router
2. THE Frontend SHALL provide a breadcrumb navigation showing current location (Projects > Project Name > Artifact)
3. WHEN a user clicks a breadcrumb item, THE Frontend SHALL navigate to that level
4. THE Frontend SHALL provide a back button to return to the previous view
5. THE Frontend SHALL update the browser URL to reflect the current navigation state

### Requirement 7: Error Handling

**User Story:** As a user, I want clear error messages when something goes wrong, so that I understand what happened and what to do next.

#### Acceptance Criteria

1. IF the Backend_API is unreachable, THEN THE Frontend SHALL display "Backend server is not available. Please ensure the backend is running."
2. IF an API request fails with 401 status, THEN THE Frontend SHALL display "Authentication failed. Please check API key configuration."
3. IF an API request fails with 404 status, THEN THE Frontend SHALL display "Resource not found."
4. IF an API request fails with 500 status, THEN THE Frontend SHALL display "Server error occurred. Please try again later."
5. THE Frontend SHALL provide a retry action for failed API requests

### Requirement 8: Loading States

**User Story:** As a user, I want to see loading indicators during data fetching, so that I know the application is working.

#### Acceptance Criteria

1. WHILE the Frontend is fetching data from Backend_API, THE Frontend SHALL display a loading spinner
2. THE Frontend SHALL disable interactive elements during loading to prevent duplicate requests
3. WHEN loading completes successfully, THE Frontend SHALL remove the loading indicator and show content
4. THE Frontend SHALL use shadcn/ui Skeleton components for content placeholders during loading
5. IF loading takes longer than 10 seconds, THE Frontend SHALL display a timeout message with retry option

### Requirement 9: Search and Filter

**User Story:** As a user, I want to search and filter artifacts, so that I can find specific documents quickly.

#### Acceptance Criteria

1. THE Frontend SHALL provide a search input that filters artifacts by title or Source_Path
2. WHEN a user types in the search input, THE Frontend SHALL update the artifact list to show only matching items
3. THE Frontend SHALL provide category filter buttons to show artifacts of specific types
4. WHEN a user selects a category filter, THE Frontend SHALL display only artifacts matching that Category
5. THE Frontend SHALL display the count of filtered results (e.g., "Showing 5 of 23 artifacts")

### Requirement 10: Version History

**User Story:** As a user, I want to see version history for artifacts, so that I can access previous versions of documents.

#### Acceptance Criteria

1. WHEN a user views an artifact, THE Frontend SHALL fetch version history from Backend_API endpoint `/api/artifacts/{artifact_id}/versions`
2. THE Frontend SHALL display a version list showing version number and creation timestamp
3. WHEN a user selects a version, THE PDF_Viewer SHALL display that specific version
4. THE Frontend SHALL highlight the currently displayed version in the version list
5. THE Frontend SHALL sort versions in descending order (newest first)

### Requirement 11: UI Component Library

**User Story:** As a developer, I want to use shadcn/ui components consistently, so that the interface has a cohesive design system.

#### Acceptance Criteria

1. THE Frontend SHALL use shadcn/ui Button component for all interactive buttons
2. THE Frontend SHALL use shadcn/ui Card component for project and artifact containers
3. THE Frontend SHALL use shadcn/ui Badge component for category labels
4. THE Frontend SHALL use shadcn/ui Skeleton component for loading states
5. THE Frontend SHALL use shadcn/ui Dialog component for modals and confirmations

### Requirement 12: API Integration

**User Story:** As a developer, I want a centralized API client, so that backend communication is consistent and maintainable.

#### Acceptance Criteria

1. THE Frontend SHALL implement an API client module that handles all Backend_API requests
2. THE API_Client SHALL include the API key in Authorization header for all requests
3. THE API_Client SHALL implement request timeout of 30 seconds
4. THE API_Client SHALL parse JSON responses and handle HTTP error statuses
5. THE API_Client SHALL provide typed TypeScript interfaces for all API responses

### Requirement 13: Build and Development

**User Story:** As a developer, I want modern build tooling, so that development is fast and production builds are optimized.

#### Acceptance Criteria

1. THE Frontend SHALL use Vite as the build tool and development server
2. WHEN running in development mode, THE Frontend SHALL enable hot module replacement
3. WHEN building for production, THE Frontend SHALL minify JavaScript and CSS assets
4. THE Frontend SHALL use TypeScript with strict type checking enabled
5. THE Frontend SHALL include ESLint and Prettier for code quality and formatting
